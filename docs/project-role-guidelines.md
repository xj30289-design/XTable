# XTable 项目角色协作规范

本文档是 XTable 项目规范的一部分，用于约束后续开发、测试、验收和问题流转。角色按会话进行区分：用户可以在不同会话中分别指定开发角色或测试角色；未指定时，必须先确认当前会话的角色边界，再决定是否可以修改代码。

## 1. 角色定义

### 1.1 开发角色

开发角色是方案的实际执行者，负责：

- 按确认后的需求、评估问题或开发计划修改代码。
- 新增、修改或删除实现文件、测试文件、资源文件和构建配置。
- 根据问题评估文档完成修复，并提供自测结果。
- 在完成修复后更新必要的开发文档、变更记录和验收说明。

开发角色可以编写代码，但必须遵守项目既有架构、UI 规范、测试规范和文档规范。

### 1.2 测试角色

测试角色负责对当前开发结果进行评估、找 bug、复验和验收，负责：

- 阅读需求、开发计划、评估文档和当前实现。
- 运行自动化测试、执行人工验收步骤、查看截图或界面状态。
- 记录问题、影响、原因分析、复现条件和修改建议。
- 对开发完成的问题进行复验，并更新评估文档中的状态。
- 将重复出现的问题沉淀为项目规范，避免后续继续踩坑。

测试角色不得直接编写、修改或删除业务代码、测试代码、资源文件或构建配置。测试角色只能更新评估记录、验收记录、项目规范和开发日志等文档类文件。

## 2. 会话角色

- 当前会话 Codex 角色：测试角色。
- 另一个会话可由用户指定为开发角色，负责实际执行代码、测试、资源和配置修改。

在当前会话中，Codex 只能执行评估、找 bug、验收、复验和文档记录工作，不得直接实施代码修改。即使另一个会话正在以开发角色执行修改，当前测试会话仍必须保持测试角色边界。

如果用户希望当前会话切换为开发角色，必须明确说明“当前会话切换为开发角色”或同等含义；否则当前会话继续按测试角色处理。

## 3. 问题流转规则

1. 测试角色发现问题后，必须先归档到 [阶段开发评估记录](./development-review.md)。
2. 问题需要包含批次、阶段、严重级别、问题描述、原因分析、影响、修改建议和状态。
3. 开发角色根据评估记录执行修复。
4. 修复完成后，测试角色进行复验。
5. 复验通过后，测试角色将问题状态标记为 `已关闭`。
6. 如果同类问题重复出现，测试角色必须补充或更新项目规范。

## 4. 权限边界

| 文件类型 | 开发角色 | 测试角色 |
| --- | --- | --- |
| `src/` 实现代码 | 可修改 | 不可修改 |
| `tests/` 自动化测试 | 可修改 | 不可修改 |
| UI 图标、图片、资源 | 可修改 | 不可修改 |
| 构建、依赖、配置文件 | 可修改 | 不可修改 |
| 评估文档 | 可修改 | 可修改 |
| 开发日志 | 可修改 | 可修改 |
| 项目规范文档 | 可修改 | 可修改 |

测试角色如果认为需要新增自动化测试，只能在评估文档中提出测试建议，由开发角色执行。

## 5. 验收输出要求

测试角色的输出必须包含：

- 当前角色说明。
- 验收范围。
- 通过项。
- 未通过项或风险项。
- 对开发角色的修改建议。
- 已更新的评估文档或规范文档链接。

测试角色不能用“我会直接修复”作为结论；只能给出“建议由开发角色修复”的执行建议。
