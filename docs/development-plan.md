# XTable MVP 开发计划

## 1. 计划定位

本文档是 XTable MVP 的独立开发计划。后续开发必须以本文档作为阶段拆分依据，并在每次进入阶段、完成阶段、调整范围或完成验收时同步更新 [开发日志](./development-log.md)。阶段审核、代码评审和人工验收发现的问题必须同步记录到 [阶段开发评估记录](./development-review.md)，作为后续开发和返工目标参考。

## 2. 技术基线

- 语言：Python。
- 桌面框架：PySide6/Qt。
- 表格核心：Qt Model/View，基于 `QAbstractTableModel` 承载配置表数据。
- 数据导入导出：Excel/CSV。
- 测试基线：`pytest` 为主，UI smoke 测试覆盖主窗口、主题切换和核心面板打开。
- MVP 不接入服务端，不实现账号、权限、云同步、实时协作和运行时格式导出。

## 3. 代码模块边界

```text
xtable/
  app/                 # 应用启动、主窗口装配、全局事件
  ui/                  # PySide6 视图、控件、主题、对话框、面板
  domain/              # 纯业务模型：Project、Table、Field、Enum、Meta、Issue
  application/         # 用例服务：打开项目、保存、编辑、校验、导入导出
  table_engine/        # Qt Model/View 表格模型、选择、编辑、撤销重做
  validation/          # 规则定义、校验器、异常检测、问题定位
  io/                  # Excel/CSV 导入导出、项目文件读写、编码处理
  logging_system/      # 操作日志、系统日志、数据变更日志、诊断信息
  persistence/         # 项目目录约定、配置、临时恢复文件
  tests/               # 单元测试、集成测试、UI smoke 测试
```

模块约束：

- `domain` 不依赖 PySide6，不读写文件，只定义业务对象、枚举、规则结果和领域行为。
- `application` 负责编排业务流程，例如打开项目、保存项目、导入表、校验项目、导出项目。
- `ui` 只负责展示和交互，不直接解析 Excel/CSV，不直接拼接日志文件。
- `table_engine` 只处理表格模型、选择、编辑命令、撤销重做和表格状态映射。
- `validation` 输出统一校验结果，供 UI、导出阻塞和日志系统共同使用。
- `io` 负责文件读写和格式转换，不承载业务规则判断。
- `logging_system` 提供统一日志 API，禁止业务模块自行写日志文件。

## 4. 开发阶段

### Phase 0：工程骨架与技术基线

- 阶段目标：建立可运行的 PySide6 桌面应用骨架。
- 输入条件：本开发计划、主需求文档、类型规格文档。
- 交付内容：Python 项目结构、依赖配置、应用入口、空主窗口、基础主题、测试命令。
- 明确不做：不实现真实项目读写，不实现表格编辑业务。
- 验收标准：应用可启动；主窗口包含顶部工具栏、中间工作区、左侧功能栏、底部状态栏；测试命令可执行。
- 关联需求：[主界面布局](./requirements.md#31-ui-与交互模块)、[字段类型规格](./specs/field-types.md)。

### Phase 1：项目与文件系统

- 阶段目标：支持创建、打开、保存本地配置项目。
- 输入条件：Phase 0 可运行应用。
- 交付内容：项目模型、项目配置、推荐目录结构、最近项目、文件安全检测、项目创建和打开 UI。
- 明确不做：不实现复杂导入导出，不实现版本工具集成命令。
- 验收标准：用户能创建并重新打开本地项目；项目设置可保存；外部修改、只读、占用冲突不会被静默覆盖。
- 关联需求：[主需求文档](./requirements.md#32-项目与文件模块)、[开发日志](./development-log.md)。

### Phase 1.5：Editor UI Demo 与 UI Kit 基座

- 阶段目标：在继续推进业务编辑功能前，完成一套独立、可组合、可切换主题、可自由调整窗口布局的编辑器 UI Demo 和 UI Kit。
- 输入条件：Phase 1 主窗口、主题、工具栏、状态栏、诊断抽屉和基础图标体系已经具备雏形。
- 交付内容：UI token、统一图标、统一按钮、统一弹窗、状态栏、诊断抽屉、表格外观、字段编辑入口、布局组件、Demo 页面和截图验收清单。
- 明确不做：不实现真实业务数据读写，不实现完整 Table/Enum/Meta 编辑逻辑，不接入真实校验和导入导出流程。
- 验收标准：Demo 可独立启动；所有核心 UI 组件可见且可切换 Light/Dark；弹窗、状态栏、诊断抽屉、表格、输入控件、工具栏和侧栏均无默认系统浅色样式露出；后续业务 UI 必须优先复用 UI Kit。
- 模块约束：后续新 UI 需求必须先进入 `xtable.ui` 实现为组件、页面、Dialog 或 Shell 能力，再由 `app`、`application` 或其他业务模块调用；非 UI 模块不得 import `PySide6`。
- 关联需求：[Editor UI Demo 规划](./editor-ui-demo-plan.md)、[UI 实现质量规范](./ui-implementation-guidelines.md)、[UI 图标规范](./ui-icon-guidelines.md)。

### Phase 2：核心数据模型

- 阶段目标：建立 Table、Field、Enum、Meta 的统一业务模型。
- 输入条件：Phase 1 项目文件结构稳定；Phase 1.5 UI Kit 已明确后续业务 UI 复用边界。
- 交付内容：表格类型、字段类型、枚举、数据元、引用关系和类型注册表。
- 明确不做：不实现完整 UI 编辑器，不实现 Excel/CSV 解析。
- 验收标准：普通表、分组表、二维表能用统一模型表达；字段能引用 Enum 和 Meta；模型层不依赖 UI。
- 关联需求：[表格类型规格](./specs/table-types.md)、[字段类型规格](./specs/field-types.md)、[全局枚举规格](./specs/enums.md)、[自定义数据元规格](./specs/meta-types.md)。

### Phase 3：表格编辑工作台

- 阶段目标：实现接近 Excel 的核心编辑体验。
- 输入条件：Phase 2 数据模型可用。
- 交付内容：`QAbstractTableModel`、单元格编辑、选择、复制粘贴、插入删除、筛选排序、查找替换、批量编辑、撤销重做。
- 明确不做：不在本阶段实现完整导入导出，不实现 Meta 升级 Table。
- 验收标准：用户能完成常见配置表编辑流程；撤销重做覆盖编辑行为；单元格状态可展示错误、警告、只读和引用标记。
- 关联需求：[字段类型规格](./specs/field-types.md)、[校验规则规格](./specs/validation-rules.md)。

### Phase 4：规则与校验系统

- 阶段目标：实现数据质量约束和异常定位。
- 输入条件：Phase 3 表格编辑可产生稳定数据变更。
- 交付内容：统一校验结果、字段规则、表格类型规则、跨表引用校验、问题报告抽屉、状态栏问题数量。
- 明确不做：不实现运行时格式导出，不实现用户自定义脚本规则。
- 验收标准：能检测类型错误、必填为空、唯一冲突、主键异常、枚举越界、引用缺失、分组和二维表结构异常；Error 阻塞导出。
- 关联需求：[校验规则规格](./specs/validation-rules.md)。

### Phase 5：导入导出

- 阶段目标：支持 Excel/CSV 作为 MVP 输入输出。
- 输入条件：Phase 4 校验系统可阻塞导出。
- 交付内容：Excel/CSV 导入、当前表导出、项目导出、导入异常报告、导出前校验、面向程序的类型与规则定义导出。
- 明确不做：不导出 JSON、Lua、Protobuf 等运行时格式。
- 验收标准：可导入多张 Excel/CSV 表；普通表、分组表、二维表按专属规则导出；导入导出失败有明确原因和日志。
- 关联需求：[表格类型规格](./specs/table-types.md)、[字段类型规格](./specs/field-types.md)、[校验规则规格](./specs/validation-rules.md)。

### Phase 6：Enum、Meta 与高级类型能力

- 阶段目标：补齐全局枚举、自定义数据元、列表字段和 Meta 升级能力。
- 输入条件：Phase 5 导入导出流程稳定。
- 交付内容：Enum 窗口、Meta 窗口、引用影响查看、列表字段编辑、嵌套深度限制、Meta 复杂度提示、Meta 升级 Table。
- 明确不做：不实现复杂脚本化数据生成，不实现云端类型库。
- 验收标准：用户能创建和维护枚举、数据元和列表字段；废弃枚举项可识别；Meta 升级 Table 有预览、冲突提示和回退方案。
- 关联需求：[全局枚举规格](./specs/enums.md)、[自定义数据元规格](./specs/meta-types.md)。

### Phase 7：日志与诊断系统

- 阶段目标：提供完整本地日志和问题复现信息。
- 输入条件：核心编辑、校验、导入导出流程已形成稳定事件。
- 交付内容：用户操作日志、系统日志、数据变更日志、异常日志、日志面板、日志滚动、诊断信息复制。
- 明确不做：不实现服务端审计平台。
- 验收标准：编辑、导入、导出、保存、校验都有日志；关键错误可生成可复制诊断信息；日志目录可被版本工具忽略。
- 关联需求：[主需求文档](./requirements.md#37-日志系统)、[开发日志](./development-log.md)。

### Phase 8：稳定性、性能与验收打磨

- 阶段目标：让 MVP 达到可交付验收状态。
- 输入条件：Phase 0 至 Phase 7 的功能已集成。
- 交付内容：性能压测、异常恢复、主题可读性检查、验收用例、打包产物。
- 明确不做：不扩展 MVP 外的账号、权限、云同步、发布管线。
- 验收标准：普通策划可在 30 分钟内完成打开项目、定位表、编辑、校验、导出流程；主需求第 5 章验收项均有记录。
- 关联需求：[主需求文档](./requirements.md#5-验收标准)。

## 5. 阶段执行规则

- 开始任何阶段前，必须更新 [开发日志](./development-log.md) 的当前状态。
- 每个阶段完成后，必须记录完成范围、未完成范围、风险和验收完整度。
- 每次阶段审核、代码评审、架构复盘或人工验收后，必须更新 [阶段开发评估记录](./development-review.md)，记录问题、影响、修改建议、严重级别和处理状态。
- 阶段进入“已完成”前，必须确认该阶段在 [阶段开发评估记录](./development-review.md) 中没有未关闭的 `P1` 问题；遗留 `P2/P3` 必须写明接受原因和后续处理阶段。
- 开发日志中的阶段进度和验收完整度必须与 [阶段开发评估记录](./development-review.md) 中未关闭问题保持一致。
- 需求变化必须先进入对应规格文档，再同步更新主需求文档索引。
- 阶段验收不得只写“完成”，必须列出可验证结果。
- 文档更新不得替代 Git commit message；两者都必须保留。
